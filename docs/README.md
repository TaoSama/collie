# 文档

## 各类文档放在哪

下面的目录和文件都是需要时才创建，和它的第一篇文档一起建。

| 路径 | 放什么 |
| --- | --- |
| `architecture.md` | 系统怎么拼起来：组件、数据流、边界。 |
| `design/` | 产品原则 `PRINCIPLES.md` 和决策记录 `DECISIONS.md`，见下面的「设计文档」。 |
| `prototypes/` | 可独立打开的交互原型（HTML 等文本格式），作为预期外观和行为的参照。 |
| `<模块>/` | 单个模块的维护指南：它现在是怎么工作的。 |
| `runbook/` | 操作手册：环境搭建、部署、发布、故障恢复。 |
| `reference/` | 项目依赖的实测数据、基准和外部事实，注明取得日期。 |
| `pitfall/` | 可复用的坑和解法，一个主题一个文件。动某个模块前先读对应的文件。 |
| `plans/` | 还有未决问题或未完成范围的方案，一个方案一个文件。不代表已经实现。 |
| `archive/` | 做完的方案和其他留作证据的记录。不是当前指令。 |

维护指南描述项目的现状。指南和归档记录不一致时，以指南为准。

## 设计文档

- `design/PRINCIPLES.md`：产品服务谁，以及几条能裁决设计分歧的原则，每条写明怎么检验。
- `design/DECISIONS.md`：每个不记下来就会被反复争论的决策一条，写明日期、背景、选了什么、放弃了什么和原因。方案做完时补一条。
- **代码里的 design token 是唯一事实来源**：颜色、字号、间距、圆角、动效的值在代码里只放一处（主题配置、CSS 变量或 token 文件）。组件使用 token，不写字面值，文档也不抄这些值。
- `design/DESIGN_SYSTEM.md`：用文字说明视觉和交互风格：什么场景用哪个 token、组件的行为、文案规则，并写明 token 所在的路径。改界面前先读。
- 仓库根目录的 `DESIGN.md` 是指向 `docs/design/DESIGN_SYSTEM.md` 的软链，和它一起创建，这样查找根目录设计文件的工具读到的是同一份内容。

## 索引

目录里的文件多到不好找时，给它加一个 `README.md` 索引，用表格列出每个文件：

- `pitfall/README.md`：`文件 | 什么时候读`。
- `archive/README.md` 和 `plans/README.md`：`文件 | 内容`。

跨模块、最常踩的坑，另外在 `CLAUDE.md` 的「最常见的坑」里留一行。

## 保持目录精简

- 目录结构就是索引：每篇文档放到上表对应的位置，不用另外列清单也能找到。文档移动或删除时，更新 `CLAUDE.md` 里引用它的每一行。
- 方案做完后，把仍然成立的内容并入指南或 pitfall 文件，再把方案移到 `archive/`。如果指南已经说全了，直接删掉方案。
- 不提交开发截图、录屏和验证产物。放在仓库外，需要时附到 PR 上。
